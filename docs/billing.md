# Billing and Stripe invoicing

Verinoo bills in **fiat**. There is no token, no on-chain payment and no
crypto conversion in this path. The billable unit is a **completed inference
task**; the buyer pays for the receipt, not for token counts. The chain's
`feesCommitted` and `balance` columns are metering evidence in chain units, not
dollar amounts, and the invoicing script ignores them when computing the total.

`scripts/stripe_invoice.py` turns one tenant's usage CSV into a Stripe invoice.
It is stdlib-only (Python 3.9+), dry-runs by default, and only calls Stripe when
`--live` is passed.

## Export usage

The node exposes the CSV export at `GET /v1/usage/:address/csv`. It is the same
snapshot as `GET /v1/usage/:address`, rendered as one CSV row:

```bash
ADDR=ai_0123456789abcdef
curl -fsS -H "Authorization: Bearer $VNN_API_KEY" \
  "https://verinoo.com/v1/usage/$ADDR/csv" \
  -o "usage-$ADDR-$(date +%F).csv"
```

Against a local node, drop the header if API keys are disabled:

```bash
curl -fsS "http://localhost:7100/v1/usage/$ADDR/csv" -o usage.csv
```

When `VNN_API_KEYS_FILE` is enabled, the bearer key is address-bound and the
path address must match the key's address; otherwise the node returns an auth
error. Export at the end of each billing period and keep the file: its SHA-256
is written into Stripe metadata and used in the idempotency key.

| Column | Meaning | Billable |
|---|---|---|
| `address` | tenant wallet address; the metering key | identity |
| `tasks` | all tasks requested by the address | no |
| `completed` | tasks whose status is `completed` | **yes** |
| `pending` | `pending` or `assigned` tasks | no |
| `failed` | failed tasks | no |
| `feesCommitted` | chain fees committed by completed tasks | no; informational |
| `balance` | chain account balance | no; informational |

`challenged` tasks count in `tasks` but are not included in `completed`,
`pending` or `failed`. They are not billed.

**The export is cumulative for the life of the chain, not a monthly delta.**
If you invoice a tenant every month, invoice the difference between this
export's `completed` value and the last already-billed export for that address.
The script bills the `completed` number in the CSV exactly as supplied, so
either write a one-row delta CSV before invoicing or keep a per-period record.
Do not run the same cumulative CSV twice; see idempotency below for retry
semantics.

## From completed tasks to a line item

One invoice gets one line item:

```text
amount_cents = round_half_up(completed * rate_cents)
```

Examples:

| Completed | Rate | Amount |
|---|---|---|
| 1,000 | 0.5 cents/task | 500 cents = $5.00 |
| 100,000 | 0.5 cents/task | 50,000 cents = $500.00 |
| 3 | 0.5 cents/task | 2 cents (1.5 rounded half-up) |

Stripe amounts are integers in the currency's minor unit (cents for USD), so
fractional-cent totals are rounded half-up. The line item's `amount` is the
total; the script does not create one line per task or set a per-task
`unit_amount`. The description records the tenant, address, completed count and
rate, and can be overridden with `--description`. `--rate-cents` is always in
minor units, and the summary format assumes a two-decimal currency; use the
default `usd` for the prices in this document.

## Pricing tiers

The public price sheet in [`product.md`](product.md) and [`pilot.md`](pilot.md):

| Plan | Price | How it is invoiced |
|---|---|---|
| Usage | **$5 per 1,000 tasks** (0.5 cents/task) | metered from the CSV; monthly |
| Design partner | **$5,000 / 8 weeks** | flat fee; not generated by this script |
| Enterprise | from **$60k / year** | contract; not generated by this script |

Rate units matter. `--rate-cents` is **cents per completed task**, and its
default is `0.5`, i.e. **$5.00 per 1,000 tasks**, the published usage price:

- A negotiated $0.50 per 1,000 rate is `--rate-cents 0.05`.
- A high-stakes rate of $0.05 per task is `--rate-cents 5`.
- Design-partner and enterprise fees are flat contract amounts. Create those
  invoices separately in Stripe (or as a separate invoice item); this script
  only meters completed tasks.

Confirm the rate in the signed order form before `--live`. A wrong
`--rate-cents` is a wrong invoice.

## Dry run, then live

Dry run is the default and performs **no network calls**:

```bash
python3 scripts/stripe_invoice.py \
  --csv usage-ai_0123456789abcdef-2026-11-30.csv \
  --tenant acme
```

The summary prints the tenant, address, aggregated row count, CSV hash, task
counts, chain-only fields, rate, amount, description and derived idempotency
key. Check the amount against the CSV before continuing.

A representative live run against Stripe test mode:

```bash
export STRIPE_SECRET_KEY=sk_test_...   # never commit this

python3 scripts/stripe_invoice.py \
  --csv usage-ai_0123456789abcdef-2026-11-30.csv \
  --tenant acme \
  --rate-cents 0.05 \
  --customer-email billing@acme.example \
  --description "Verinoo usage 2026-11" \
  --live
```

Useful flags:

| Flag | Default | Notes |
|---|---|---|
| `--csv PATH` | required | export from `/v1/usage/:address/csv` |
| `--tenant NAME` | required | customer/invoice label and metadata |
| `--rate-cents CENTS` | `0.5` | cents per completed task; fractional values allowed |
| `--currency CODE` | `usd` | three-letter code passed to Stripe |
| `--customer-email EMAIL` | none | used to find an existing customer; omit and the script searches by name |
| `--description TEXT` | generated | invoice and line-item description |
| `--dry-run` | default | print only; no Stripe calls |
| `--live` | off | requires `STRIPE_SECRET_KEY`; creates and finalizes |
| `--idempotency-key KEY` | derived | overrides the base key |

The script accepts multiple CSV rows **only when they share one address**,
summing the columns (useful when you deliberately split a tenant's usage across
rows). It refuses a CSV with more than one distinct address, missing columns,
duplicate columns, negative/non-integer counters, zero data rows, or a computed
live amount of zero. Exit codes: `0` success, `1` Stripe/transport error, `2`
malformed input or missing configuration.

`--live` refuses to run without a non-empty `STRIPE_SECRET_KEY`. The key is
read only from the environment and is never printed.

## Stripe test mode

1. In the Stripe Dashboard, switch to **Test mode** and copy the secret key
   (`sk_test_...`) from Developers → API keys.
2. Export it as `STRIPE_SECRET_KEY` in the shell. Do not put it in a file that
   is committed.
3. Run the dry run and reconcile `completed`, rate and amount by hand.
4. Run the same command with `--live`. The script:
   - searches `GET /v1/customers?email=...` when `--customer-email` is given,
     otherwise searches by name with the Customer Search API;
   - creates a customer with `POST /v1/customers` if none is found;
   - creates one pending item with `POST /v1/invoiceitems`;
   - creates the invoice with `POST /v1/invoices` and `auto_advance=false`.
     It uses `collection_method=send_invoice` (with `days_until_due=30`) when
     the customer has an email; without an email it uses
     `charge_automatically` with automatic collection off, which still leaves
     the invoice open and unpaid;
   - finalizes it with `POST /v1/invoices/{id}/finalize`.
5. Inspect the invoice in the test Dashboard. It should be **open/finalized,
   not paid**. The script never calls a pay endpoint and does not collect
   payment; the customer pays through the hosted invoice page.
6. Void or delete the test invoice/customer when done, or use a test clock if
   you are testing renewal dates.

Test-mode invoices never move real money. Repeat with a live key only after the
test run, CSV hash and amount have been reviewed. Stripe's card minimum is
normally $0.50; very small pilots may need a minimum invoice or a prepaid
credit rather than a per-task invoice.

## Idempotency

Every `POST` carries an `Idempotency-Key` header. The base key is:

```text
verinoo-invoice- + sha256(raw_csv_bytes || 0x00 || tenant || 0x00 ||
                          canonical_rate || 0x00 || currency)
```

Each step appends a suffix: `-customer`, `-invoice-item`, `-invoice`,
`-finalize`. `canonical_rate` strips trailing zeros, so `0.5` and `0.50`
produce the same key. The dry-run summary prints the base key.

Consequences:

- Retrying the same CSV, tenant, rate and currency within Stripe's idempotency
  window (24 hours) returns the same customer/item/invoice instead of creating
  duplicates. This is what makes a failed or interrupted live run safe to retry.
- Changing the CSV, tenant, rate or currency changes the base key.
- Changing only `--description` or `--customer-email` does **not** change the
  key. Stripe rejects a reused key with different parameters. Within 24 hours,
  pass an explicit `--idempotency-key` if you need different parameters for the
  same usage data.
- After Stripe expires the key, a rerun can create a second invoice. Keep the
  invoice ID in your billing records and check Stripe before rerunning a live
  command.
- An explicit `--idempotency-key` is treated as the base and still gets the
  per-step suffixes.

## Refunds, credits and adjustments

The script intentionally does not refund, void, credit or pay anything.

- **Before payment:** void the open invoice in the Stripe Dashboard and reissue
  with corrected parameters and a new idempotency key (or an explicit
  `--idempotency-key`). A finalized `send_invoice` invoice is not charged
  automatically.
- **After payment:** issue a refund or credit note in Stripe. For an over-billed
  period, a credit note against the invoice is usually clearer than a cash
  refund; for an under-billed period, issue a supplemental invoice.
- **Use a negative invoice item before finalization** if you want the credit to
  appear on the same invoice. The script does not add adjustment items, so this
  is a manual Stripe operation.
- **Failed and pending tasks are not billable.** If a billed completed task is
  later disputed or found invalid, decide the credit policy from the contract
  and verify the receipt with `GET /v1/verify/:taskId`; there is no automatic
  link between verification and billing.
- **SLA credits** are commercial adjustments. Record the reason in the credit
  note or invoice metadata so the chain usage export and the invoice remain
  reconcilable.

## No token

This is fiat invoicing only. Do not convert `feesCommitted` or `balance` into
dollars, subtract them from the invoice, or ask the customer to pay in a token.
Those fields are chain accounting and stay on-chain. The Stripe invoice is paid
by card, bank transfer or whatever collection method the Stripe account
supports; no wallet signature is involved.

## Stripe API assumptions

- API base is `https://api.stripe.com`; no `Stripe-Version` is pinned, so the
  account's default API version applies.
- Customer lookup uses the list-customers `email` filter when an email is
  supplied, and the Customer Search API (`name:"..."`) when it is not. Search
  indexing is eventually consistent; pass `--customer-email` when you need a
  deterministic match.
- The script creates the invoice item first and then includes pending items
  when creating the invoice. It assumes the tenant's Stripe customer has no
  unrelated pending invoice items; use a dedicated customer per tenant.
- Invoices are created and finalized with `auto_advance=false`, so Stripe does
  not run automatic collection, reminders or retries. The script uses
  `collection_method=send_invoice` and `days_until_due=30` when the customer has
  an email. A `send_invoice` invoice cannot be created without an email, so the
  script falls back to `collection_method=charge_automatically` with automatic
  collection off when no email is available. Finalization leaves the invoice
  open and does not pay it; there is no default payment method on a
  script-created customer.
- Invoice items are pending until invoice creation and are pulled in with
  `pending_invoice_items_behavior=include`.
- Amounts are integer minor units; the script rounds half-up before calling
  Stripe. `currency` is passed through as a lowercase three-letter code.
- Idempotency keys are stored by Stripe for 24 hours. The script cannot make an
  old key permanent.
